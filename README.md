# RehearseAI

RehearseAI is a local browser voice mock-interview coach. It uses a delivery-aware opening and four-question controller, SmallWebRTC browser transport, Deepgram streaming STT, OpenAI text LLM, Cartesia streaming TTS by default, and local session logs. OpenAI TTS remains a selectable fallback. Conversational and voice quality still need a microphone and listening test.

The latest real session (`ec438fc5-14a2-4cac-b0df-076ccd16b70a`) showed model-proposed “clarifications” acting as second project probes after a follow-up, including a repeated metric request on question three and another probe after question four's follow-up answer. It also classified “Definitely now on what?” as a coach-directed detour. The controller now shares one project-probe slot across follow-up, nudge, and model clarification; explicit candidate repeat/explanation requests retain a separate bounded slot. The session route rejects a second probe, retains clearly unfinished thoughts, accepts a clear “I don't know” or refusal without another probe, and moves from question four to feedback after its answered optional probe. A short question about the scope of question four gets a project-grounded explanation. Raw STT text is preserved, while the decision prompt asks the model to use context for likely recognition errors. A four-case real text-model check found that the model still chose `wait` on two completed answers and `detour` on the Q4 scope question, so Python's routing guards remain necessary. A microphone check is still required. [PROMPTS.md](PROMPTS.md) records the cases and results.

The earlier recurring OpenAI no-audio warning was traced to Pipecat's TTS context timeout, which could expire before that provider returned its first chunk. The 20-second idle override remains only on the OpenAI fallback. Cartesia uses Pipecat 1.14.0's own three-second idle boundary: its WebSocket receive loop appends audio and closes the context on the provider's `done` event, while interruption sends a context-specific `cancel` message. A bounded real Pipecat check produced audio after an interruption, with no cancelled-context audio reaching the test sink afterward. This is not a browser playback or microphone test. See [TTS_DIAGNOSIS.md](TTS_DIAGNOSIS.md) for the historical OpenAI timeline and [TTS_COMPARISON.md](TTS_COMPARISON.md) for the six direct requests and Pipecat check.

## Run locally

Use Python 3.11+ and [uv](https://docs.astral.sh/uv/getting-started/installation/). Create `.env` from `.env.example`, then set these server-side credentials for the default configuration:

- `DEEPGRAM_API_KEY` — [Deepgram API key](https://developers.deepgram.com/docs/create-additional-api-keys)
- `OPENAI_API_KEY` — [OpenAI API key](https://platform.openai.com/api-keys), used for the text LLM
- `CARTESIA_API_KEY` — [Cartesia API key](https://play.cartesia.ai/keys), used for default TTS

Set `REHEARSE_TTS_PROVIDER=openai` to use OpenAI TTS instead; then `CARTESIA_API_KEY` is not required. Provider-specific model and voice settings are listed in `.env.example`. There is no automatic provider switch during a response.

Never place keys in browser code. `.env` and `sessions/` are ignored by Git. Start with one command:

```sh
uv run python -m rehearse_ai
```

Open `http://127.0.0.1:7860/`, choose **Start interview**, allow microphone access, and use headphones if possible. The desktop workspace is at most 1180px wide; its 40/60 cards share the explicit height `clamp(420px, calc(100dvh - 200px), 620px)`. The conversation header stays fixed while its transcript body scrolls. On narrow screens the cards stack and the conversation card has a bounded height. The opening does not display question-one progress; the four segments reflect the current main question when its server output starts. The transcript uses “RehearseAI” and “You” labels above compact message bubbles, merges continuation turns, and marks output interrupted after it began. It follows new turns only when the reader is near the bottom; **Jump to latest** appears when the reader scrolls up. The transcript can be focused for keyboard scrolling. Session and build IDs are in collapsed Diagnostics; actionable voice warnings stay visible. **End session** immediately closes WebRTC and stops local microphone tracks. After normal or spoken early closing, status briefly shows **Finishing** while buffered browser audio is allowed to drain; the page then closes media and offers **Start again**. The server binds only to a loopback address. A browser with WebRTC and microphone support is required; localhost is a secure context for microphone permission.

The server prints a `RehearseAI build <version>+<source hash>` identifier at startup. The same value appears in `/healthz`, in the browser's collapsed Diagnostics section, and in new session logs. It is a fingerprint of packaged source and browser assets when the process starts, including uncommitted edits; it does not change inside a running process. After a restart, hard-refresh the browser and compare its build with `curl http://127.0.0.1:7860/healthz`. If port 7860 is already occupied, inspect it with `lsof -nP -iTCP:7860 -sTCP:LISTEN` and `ps -p <PID> -o pid,ppid,lstart,command`. Stop only the confirmed RehearseAI process with Ctrl-C in its terminal (or `kill -TERM <PID>`), then run the command above again.

`.env.example` lists configurable port, models, voices, VAD thresholds, turn pause, and session directory. Defaults are Deepgram `nova-3-general`, OpenAI text `gpt-4.1-mini`, and Cartesia `sonic-3.6` with Skylar voice ID `db6b0ed5-d5d3-463d-ae85-518a07d3c2b4`. These are separate STT → text LLM → TTS calls. The LLM's structured `run_inference()` call returns a complete JSON response before validation, so no unvalidated control text can enter TTS. Pipecat's Cartesia service streams audio over WebSocket. No realtime or speech-to-speech model is used.

## Opening and voice

The coach begins with **“Hey, I'm RehearseAI, your AI interview coach. How's your day going?”** After the candidate responds, the text LLM writes one brief acknowledgement. Unless the candidate already supplied a clear preferred name or asked to start, Python asks **“What should I call you?”** Sharing a name is optional and scoped to the session. A name reply gets a brief acknowledgement and **“Ready to jump in?”** A clear request to start skips name collection and readiness; a name already given in the greeting skips name collection. “Not ready yet” retains the deferred-readiness path. The four-question format and short feedback appear in the browser, not in speech. Each coach utterance asks at most one question. Opening turns do not count as interview answers or spend follow-up or clarification allowances. Interrupted or unheard opening/name/readiness utterances retain delivery-aware retry behavior; spoken stop remains the highest-priority, latched route.

During a project question, a question directed at the coach can take a brief detour. Asking why the coach did not ask for a name prompts an optional name reply. A known name is acknowledged without collecting it again. The structured decision prompt can identify other conversational detours, but Python validates the response, preserves any literal project-answer fragment, and keeps the same question and project allowances. The decision prompt receives the exact current answer and the latest candidate turn. Interview-relevant detours return to the pending project prompt after delivery; feedback and off-topic boundaries ask whether to continue or finish and wait for that choice. The controller gives at most two short choice or presence replies to unrelated turns, then closes neutrally rather than leaving a silent pending choice. These are routing rules, not proof that the LLM always recognizes a detour in live speech.

Readiness distinguishes affirmative, deferred, and unclear answers after normalizing punctuation, contractions, and repeated words. A plain “No” to “Ready to jump in?” is deferred, not unclear. A clear “start,” “I'm ready,” or “let's get into it” starts question one, even after an earlier “not yet.” A deferred answer receives one wait cue; an unclear answer receives one specific readiness clarification. Once either allowance is spent, further nonaffirmative turns remain in the readiness gate and publish visible guidance instead of silently disappearing. A clear affirmative or spoken stop still works. Repeat limits likewise publish guidance; if a repeat interrupts the opening acknowledgement after its limit is spent, acknowledgement generation resumes. A provider or speech queue failure is logged as `response_error` and shown in the browser. These bounds avoid an endless spoken readiness exchange.

## Behavior and evidence

Python owns the four exact main questions, their order, one substantive follow-up or nudge per question, and one clarification or repeat per question. The LLM proposes a short contextual action from actual answers and receives the exact current question, its answer, the last delivered prompt, allowance counts, and interruption context. Older answers are background only. Explicit spoken stop, repeat, and skip requests are handled before inference. Normal closing feedback is generated from session answers as 2–3 short sentences; an early stop enters a separate state and offers a 1–2 sentence closing based only on collected answers. With no collected answer, it gives a short generic closing. No keyword grading is used. The exact runtime prompts are linked in [PROMPTS.md](PROMPTS.md).

Pipecat VAD and one `SpeechTimeoutUserTurnStopStrategy` detect speech and decide when a candidate turn ends. Its silence policy now defaults to **1.1 seconds** (`REHEARSE_TURN_PAUSE_SECS`), a starting point for a live tuning experiment. The Pipecat turn processor's 30-second watchdog remains a failure fallback. Pipecat's interruption frame cancels in-flight TTS/output promptly on speech start, independently of the longer completion wait. The session cancels obsolete LLM inference. Final STT segments are accumulated until Pipecat reports the completed turn; the browser merges continuation turns into a readable answer while the JSONL log retains each raw segment. An incomplete answer may yield a silent `wait` decision. A rejected extra prompt never forces advancement. Stale delivery IDs cannot advance the controller.

The browser shows “Preparing first question — wait for audio” while the initial question is queued, without displaying queued text as spoken transcript. The microphone remains available for interruption or spoken termination. Server output start is only an approximation of browser playback.

Each attempt writes `sessions/<uuid>.jsonl` with ordered UTC timestamps and a common server monotonic `session_elapsed_ms` clock, utterance IDs, candidate transcription, and nullable latency. Events include estimated VAD speech end, Pipecat turn completion, final STT receipt, LLM request/validated decision, TTS request/first generated audio, first server output, cancellation, and delivery. Pipecat's structured inference does not expose a first-token time here, and WebRTC does not expose reliable per-utterance browser playback onset; both remain null. Generated audio is logged as generated, not played. The recorded latency is **candidate turn stop → server output start**, an approximation; it is not browser playback latency. Delivery acknowledgment uses Pipecat's `BotStoppedSpeakingFrame` after the output transport only when the matching utterance had audio output and TTS completion and was not cancelled. Pipecat may also emit that frame on interruption, so cancelled output stops are ignored. This remains server-side evidence, not proof every word played in the browser or was heard. On a terminal interview event, the browser allows 1.2 seconds after this server-side output stop for buffered playout, then stops the microphone and connection automatically; WebRTC provides no reliable per-utterance browser drain event, so this delay is an approximation and could still be too short on a congested connection. Manual End is immediate. The browser shows `Thinking` while a response is prepared and adds RehearseAI text to the transcript only when server output starts. It never labels that event as confirmed browser playback; raw delivery events remain in JSONL logs.
