# RehearseAI

RehearseAI is a local browser voice mock-interview coach. It uses a delivery-aware opening and four-question controller, SmallWebRTC browser transport, Deepgram streaming STT, OpenAI text LLM, OpenAI TTS, and local session logs. Conversational opening and detour changes have offline checks; their spoken quality still needs a microphone test.

The recurring no-audio warning was traced to Pipecat's TTS context timeout, which could expire before the configured OpenAI voice returned its first chunk. A real instrumented request first yielded audio at 9.673 seconds, after an eight-second context timeout had already reported silence. The targeted fix uses a 20-second context timeout and discards late audio from cancelled contexts. See [TTS_DIAGNOSIS.md](TTS_DIAGNOSIS.md) for the exact timelines, bounded paid checks, and remaining live verification. A genuinely silent response may now take up to 17 additional seconds to report.

## Run locally

Use Python 3.11+ and [uv](https://docs.astral.sh/uv/getting-started/installation/). Create `.env` from `.env.example`, then set the two required server-side credentials:

- `DEEPGRAM_API_KEY` — [Deepgram API key](https://developers.deepgram.com/docs/create-additional-api-keys)
- `OPENAI_API_KEY` — [OpenAI API key](https://platform.openai.com/api-keys), used for both text LLM and TTS

Never place keys in browser code. `.env` and `sessions/` are ignored by Git. Start with one command:

```sh
uv run python -m rehearse_ai
```

Open `http://127.0.0.1:7860/`, choose **Start interview**, allow microphone access, and use headphones if possible. The browser shows connection and microphone state, the current question, and the transcript. **End session** closes WebRTC and stops local microphone tracks. The server binds only to a loopback address. A browser with WebRTC and microphone support is required; localhost is a secure context for microphone permission.

The server prints a `RehearseAI build <version>+<source hash>` identifier at startup. The same value appears in `/healthz`, in the session card, and in new session logs. It is a fingerprint of packaged source and browser assets when the process starts, including uncommitted edits; it does not change inside a running process. After a restart, hard-refresh the browser and compare its build with `curl http://127.0.0.1:7860/healthz`. If port 7860 is already occupied, inspect it with `lsof -nP -iTCP:7860 -sTCP:LISTEN` and `ps -p <PID> -o pid,ppid,lstart,command`. Stop only the confirmed RehearseAI process with Ctrl-C in its terminal (or `kill -TERM <PID>`), then run the command above again.

`.env.example` lists configurable port, models, voice, speaking speed, VAD thresholds, turn pause, and session directory. Defaults are Deepgram `nova-3-general`, OpenAI text `gpt-4.1-mini`, and OpenAI TTS `gpt-4o-mini-tts` with voice `shimmer` at speed `1.0`. These are separate STT → text LLM → TTS calls. OpenAI TTS avoids a third provider account; the available Cartesia key is not used. The LLM's structured `run_inference()` call returns a complete JSON response before validation, so no unvalidated control text can enter TTS. Pipecat's OpenAI TTS service streams generated audio chunks. Provider and transport delay contributions have not yet been measured separately in a real session. No realtime or speech-to-speech model is used.

## Opening and voice

The coach begins with **“Hey, I'm RehearseAI, your AI interview coach. How's your day going?”** After the candidate responds, the text LLM writes one brief acknowledgement. Unless the candidate already supplied a clear preferred name or asked to start, Python asks **“What should I call you?”** Sharing a name is optional and scoped to the session. A name reply gets a brief acknowledgement and **“Ready to jump in?”** A clear request to start skips name collection and readiness; a name already given in the greeting skips name collection. “Not ready yet” retains the deferred-readiness path. The four-question format and short feedback appear in the browser, not in speech. Each coach utterance asks at most one question. Opening turns do not count as interview answers or spend follow-up or clarification allowances. Interrupted or unheard opening/name/readiness utterances retain delivery-aware retry behavior; spoken stop remains the highest-priority, latched route.

During a project question, a question directed at the coach can take a brief detour. Asking why the coach did not ask for a name prompts an optional name reply, then resumes the pending project prompt. A known name is acknowledged without collecting it again. The structured decision prompt can identify other conversational detours, but Python validates the response, preserves any literal project-answer fragment, and keeps the same question and project allowances. The decision prompt receives the exact current answer and the latest candidate turn. General detours are limited to two distinct replies per main question; beyond that the controller gives a short return cue. A main question or unanswered follow-up is reissued after a detour; an already collected answer is kept for the next decision. These are routing rules, not proof that the LLM always recognizes a detour in live speech.

Readiness distinguishes affirmative, deferred, and unclear answers after normalizing punctuation, contractions, and repeated words. A clear “start,” “I'm ready,” or “let's get into it” starts question one, even after an earlier “not yet.” A deferred answer receives one wait cue; an unclear answer receives one specific readiness clarification. Once either allowance is spent, further nonaffirmative turns remain in the readiness gate and publish visible guidance instead of silently disappearing. A clear affirmative or spoken stop still works. Repeat limits likewise publish guidance; if a repeat interrupts the opening acknowledgement after its limit is spent, acknowledgement generation resumes. A provider or speech queue failure is logged as `response_error` and shown in the browser. These bounds avoid an endless spoken readiness exchange.

`REHEARSE_TTS_VOICE` selects a built-in OpenAI voice; `shimmer` is a provisional female-sounding choice for the coach. `REHEARSE_TTS_SPEED=1.0` keeps the provider's normal pace. With `gpt-4o-mini-tts`, the runtime [TTS style prompt](src/rehearse_ai/prompts/tts_style.txt) asks for a calm, clear, friendly delivery with restrained expression. The [OpenAI Speech API](https://developers.openai.com/api/reference/resources/audio/subresources/speech/methods/create) supports these instructions and a 0.25–4.0 speed range for that model; instructions are omitted if `tts-1` is selected. The [voice guide](https://developers.openai.com/api/docs/guides/text-to-speech) lists `shimmer` among supported voices and offers previews. It does not establish that this voice will sound female or natural to every listener, and text instructions cannot guarantee delivery quality. This Speech API model is currently [deprecated with a January 6, 2027 shutdown date](https://developers.openai.com/api/docs/guides/text-to-speech); a future cascaded TTS replacement will be needed if the project continues beyond that date. The current assignment disallows realtime speech-to-speech models.

## Behavior and evidence

Python owns the four exact main questions, their order, one substantive follow-up or nudge per question, and one clarification or repeat per question. The LLM proposes a short contextual action from actual answers and receives the exact current question, its answer, the last delivered prompt, allowance counts, and interruption context. Older answers are background only. Explicit spoken stop, repeat, and skip requests are handled before inference. Normal closing feedback is generated from session answers as 2–3 short sentences; an early stop enters a separate state and offers a 1–2 sentence closing based only on collected answers. With no collected answer, it gives a short generic closing. No keyword grading is used. The exact runtime prompts are linked in [PROMPTS.md](PROMPTS.md).

Pipecat VAD and one `SpeechTimeoutUserTurnStopStrategy` detect speech and decide when a candidate turn ends. Its silence policy now defaults to **1.1 seconds** (`REHEARSE_TURN_PAUSE_SECS`), a starting point for a live tuning experiment. The Pipecat turn processor's 30-second watchdog remains a failure fallback. Pipecat's interruption frame cancels in-flight TTS/output promptly on speech start, independently of the longer completion wait. The session cancels obsolete LLM inference. Final STT segments are accumulated until Pipecat reports the completed turn; the browser merges continuation turns into a readable answer while the JSONL log retains each raw segment. An incomplete answer may yield a silent `wait` decision. A rejected extra prompt never forces advancement. Stale delivery IDs cannot advance the controller.

The browser shows “Preparing first question — wait for audio” while the initial question is queued, without displaying queued text as spoken transcript. The microphone remains available for interruption or spoken termination. Server output start is only an approximation of browser playback.

Each attempt writes `sessions/<uuid>.jsonl` with ordered UTC timestamps and a common server monotonic `session_elapsed_ms` clock, utterance IDs, candidate transcription, and nullable latency. Events include estimated VAD speech end, Pipecat turn completion, final STT receipt, LLM request/validated decision, TTS request/first generated audio, first server output, cancellation, and delivery. Pipecat's structured inference does not expose a first-token time here, and WebRTC does not expose reliable per-utterance browser playback onset; both remain null. Generated audio is logged as generated, not played. The recorded latency is **candidate turn stop → server output start**, an approximation; it is not browser playback latency. Delivery acknowledgment uses Pipecat's `BotStoppedSpeakingFrame` after the output transport only when the matching utterance had audio output and TTS completion and was not cancelled. Pipecat may also emit that frame on interruption, so cancelled output stops are ignored. This remains server-side evidence, not proof every word played in the browser or was heard. The browser shows “Preparing response” while TTS is pending and adds coach text to the transcript only when server output starts, labeling its status explicitly.
