# Runtime prompts

The exact runtime text is loaded from the versioned files [opening_ack.txt](src/rehearse_ai/prompts/opening_ack.txt), [decision.txt](src/rehearse_ai/prompts/decision.txt), [feedback.txt](src/rehearse_ai/prompts/feedback.txt), [early_feedback.txt](src/rehearse_ai/prompts/early_feedback.txt), and [tts_style.txt](src/rehearse_ai/prompts/tts_style.txt). This document does not duplicate their text.

The opening call receives the candidate's `greeting_response` and Python's `greeting_readiness` classification as data. It returns one short acknowledgement in structured JSON. The runtime prompt asks it to answer “How are you?” naturally without inventing human experiences, avoid parroting and canned cheer, and acknowledge nervousness or a difficult day gently. Python rejects an acknowledgement that contains another question or is too long. If generation or validation fails, a brief neutral fallback is used; a reciprocal question receives “Doing well, thanks.” Python then asks one optional name question unless an explicit preferred name, refusal, or clear start request was already heard. It acknowledges a name and checks readiness in a separate utterance. Question one is prepared only after the appropriate opening delivery event. The four-question format and short feedback appear on screen rather than in speech. The LLM cannot choose the first project question. One name repeat is allowed; another repeat moves to readiness rather than looping. Existing readiness wait, clarification, and repeat limits remain. Explicit stop requests bypass inference. Opening turns do not consume interview answer or follow-up budgets. The TTS style file is sent only when the configured model is `gpt-4o-mini-tts`; `tts-1` does not support speech instructions. Speed is a separate numeric provider setting.

The decision call receives the current fixed question, `current_question_answer`, `latest_candidate_turn`, the last delivered and project prompts, interruption context, `answers_by_question_before_latest_turn`, and Python-owned reply allowances as JSON data. Its structured response can distinguish `feedback_request`, `off_topic`, and `coach_identity` from project `follow_up`, `nudge`, `clarification`, `wait`, and `advance`. A feedback request produces a separately marked provisional response grounded in earlier collected answers; it is not final feedback. An off-topic action uses a fixed interview-scope boundary. An actual coach-identity question gets a fixed identity answer. A brief conversation response ends with a Python-owned continue/finish question. Delivery enters a waiting choice state; no project prompt is automatically appended. A `continue` choice restores the preserved question with a fresh utterance ID, while `finish` enters early closing. Python gives at most two short choice or presence replies to unrelated turns; the next such turn ends early instead of waiting silently. Explicit stop retains priority. For an interrupted project prompt, one decision call interprets the turn before it can be committed as an answer; the same result is used for a substantive answer when output had started. An unheard prompt is preserved and retried after a non-detour turn. The one exceptional corrective call is a bounded retry if the model answers a coach-identity question that was not asked. Python also normalizes a model's generic `detour` identity reply when an actual identity question was asked. Project answer snapshots are restored for detours, and a `project_fragment` is retained only if it is a literal span. Detours do not spend project allowances. Model-proposed follow-ups, nudges, and clarifications share **one** project-probe slot. Candidate-requested repeats use a separate bounded slot. Normal final feedback supplies 2–3 lines; early closing supplies 1–2 lines using collected answers only. No JSON response is sent directly to TTS. Candidate transcript content is treated as data, not instructions.

## Current routing and project-example prompt

The same versioned `decision.txt` receives a `phase` (`name`, `readiness`, `interview`, `interrupted_turn`, `continuation_choice`, or a no-project recovery phase), `project_established`, the accumulated current answer, and the latest turn. The schema includes `project_status` (`technical_example`, `no_example`, `nontechnical`, `unclear`) and `tone` (`neutral`, `gentle`). Python handles clear stop, repeat, and skip requests before inference. During an ordinary project turn, the existing decision call identifies conversational detours with no separate intent call. Interrupted project turns require one interpretation call before assigning speech to an answer; a substantive result is reused for its project decision. Python blocks a move from question one to dependent questions when no technical example is established. One alternative invitation and one scope explanation bound no-project recovery. The early-closing prompt forbids invented project praise when the candidate stops without an example.
