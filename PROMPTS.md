# Runtime prompts

The exact runtime text is loaded from the versioned files [opening_ack.txt](src/rehearse_ai/prompts/opening_ack.txt), [decision.txt](src/rehearse_ai/prompts/decision.txt), [feedback.txt](src/rehearse_ai/prompts/feedback.txt), [early_feedback.txt](src/rehearse_ai/prompts/early_feedback.txt), and [tts_style.txt](src/rehearse_ai/prompts/tts_style.txt). This document does not duplicate their text.

The opening call receives the candidate's `greeting_response` and Python's `greeting_readiness` classification as data. It returns one short acknowledgement in structured JSON. The runtime prompt asks it to answer “How are you?” naturally without inventing human experiences, avoid parroting and canned cheer, and acknowledge nervousness or a difficult day gently. Python rejects an acknowledgement that contains another question or is too long. If generation or validation fails, a brief neutral fallback is used; a reciprocal question receives “Doing well, thanks.” Python then asks one optional name question unless an explicit preferred name, refusal, or clear start request was already heard. It acknowledges a name and checks readiness in a separate utterance. Question one is prepared only after the appropriate opening delivery event. The four-question format and short feedback appear on screen rather than in speech. The LLM cannot choose the first project question. One name repeat is allowed; another repeat moves to readiness rather than looping. Existing readiness wait, clarification, and repeat limits remain. Explicit stop requests bypass inference. Opening turns do not consume interview answer or follow-up budgets. The TTS style file is sent only when the configured model is `gpt-4o-mini-tts`; `tts-1` does not support speech instructions. Speed is a separate numeric provider setting.

The decision call receives the current fixed question, `current_question_answer` with all collected turns for that question joined in order, `latest_candidate_turn`, the last delivered prompt, interruption context, older answers as background, and the remaining Python-owned reply and detour allowances as JSON data. Its structured response proposes `follow_up`, `nudge`, `clarification`, `wait`, `advance`, or `detour` plus text and an optional literal `project_fragment`. A direct question about name collection is routed by Python before project-answer submission; other coach-directed conversational questions may be proposed as a `detour`. A detour reply is brief and returns to the same main question or unanswered follow-up. Python restores the previous answer snapshot and accepts a `project_fragment` only when it is a literal span of the candidate's latest turn. Detours do not spend project follow-up or clarification allowances. The prompt still keeps question-two follow-ups on the technical challenge and forbids repeating details already provided. `wait` keeps an incomplete answer open; an exhausted allowance never authorizes automatic advancement. Spoken stop/repeat/skip requests are handled outside the LLM. Normal feedback supplies 2–3 lines; early closing supplies 1–2 lines using collected answers only. No JSON response is sent directly to TTS. Candidate transcript content is treated as data, not instructions.

## Observed prompt iteration

The real session `sessions/88284b02-e5ae-437f-95ef-2c5dd1e4edd0.jsonl` shows the candidate asking “Okay. So you'll not ask me my name?” after question one. The prior decision produced a project nudge instead of addressing the question. The next name-related turn produced a clarification about the project question. This iteration gives name collection its own Python state and instructs the decision prompt to distinguish other coach-directed questions from project answers. Mocked routing tests cover the new control path. Whether the updated prompt reliably recognizes conversational detours in real speech remains untested.

## Current routing and project-example prompt

The same versioned `decision.txt` now receives a `phase` (`name`, `readiness`, `interview`, or one of two no-project recovery phases), `project_established`, the complete accumulated current answer, and the latest turn. Its validated schema adds `project_status` (`technical_example`, `no_example`, `nontechnical`, `unclear`) and `tone` (`neutral`, `gentle`). Python handles clear stop, repeat, and skip requests before inference. A direct question about the coach's name has a fixed answer; other opening questions use one structured decision call only when needed. During project questions, the existing decision call identifies conversational detours, so no extra intent request is added there. Python validates the decision and blocks a move from question one to dependent questions when the candidate has no technical example. One alternative invitation and one scope explanation bound the recovery. The early-closing prompt explicitly forbids invented project praise when the candidate stops without an example.

No new prompt experiment has been run. Mocked decisions test Python routing, not the real model's classification or spoken quality.

Offline tests check prompt loading, structured schemas, and routing. They do not establish how naturally the acknowledgement or TTS style sounds. A real listening comparison remains pending.
