# RehearseAI implementation plan

## Architecture

RehearseAI runs on Python 3.11+ with Pipecat 1.14.0. `config.py` validates local settings. `interview.py` is the provider-independent state machine for the opening, fixed questions, and closing. `session.py` maps candidate and agent events to it, cancels obsolete inference, and writes `session_log.py` events. `pipeline.py` assembles SmallWebRTC input → Silero VAD → Deepgram streaming STT → Pipecat user-turn processor → interview adapter → OpenAI TTS → audio/utterance observer → SmallWebRTC output → delivery observer. The OpenAI text LLM is called through Pipecat's `run_inference()` for a structured opening acknowledgement, interview decision, or closing feedback; its JSON is never spoken directly. `server.py` serves the package's `web/` assets and WebRTC offer endpoint. Runtime prompts live in `src/rehearse_ai/prompts/` and are documented in `PROMPTS.md`.

Python asks these main questions exactly and in order:

1. Tell me about a project you're proud of.
2. What was the hardest technical problem in it?
3. How did you know it was working well?
4. What would you do differently now?

The controller first delivers “Hey, how's it going?” and collects a response. A structured LLM call produces one short acknowledgement. Python appends “Ready to jump in?” only when readiness is unclear; a clearly ready greeting gets the acknowledgement alone, followed by question one only after delivery. A deferred greeting gets a short wait cue. The four-question format and short feedback are explained in the browser. One wait cue, one unclear-readiness clarification, and one repeat of each opening prompt bound spoken prompting. Further unrecognized or deferred turns publish actionable browser guidance; a clear “start” or stop command still works. Opening speech does not spend question allowances. The LLM may then propose a context-aware follow-up, nudge, clarification, wait, or advance. Python limits each question to one substantive follow-up/nudge and one clarification/repeat, selects each next main question, and blocks progress after closing feedback delivery. A `wait` decision leaves a fragmented answer open, and a rejected proposal never implicitly advances. Explicit spoken end, repeat, and skip requests are handled before LLM inference. Candidate text is untrusted data. Normal closing feedback uses actual recorded answers and contains 2–3 short spoken sentences. Early termination enters a distinct controller state and offers a 1–2 sentence closing based on collected answers only.

## Delivery and interruption contract

An agent utterance is first *prepared* with a session-scoped ID. A marker before `TTSSpeakFrame` correlates it with Pipecat's TTS context ID. Generation does not count as delivery. `BotStartedSpeakingFrame` is accepted only after a generated audio chunk for the pending ID; `BotStoppedSpeakingFrame` can acknowledge delivery only after the matching TTS context finishes and no cancellation invalidated the utterance. Pipecat's output transport can emit `BotStoppedSpeakingFrame` during interruption, so a stop from cancelled output is consumed without delivery. Duplicate and stale controller IDs are ignored. Pipecat bot speaking frames lack utterance IDs, so the server correlates them using the pending output state; an ambiguous late frame is treated conservatively. These server events do not prove browser playout or human hearing. The browser omits prepared text from the conversation transcript, shows it only after server output begins, and marks interruption/completion.

Pipecat `UserTurnProcessor` uses VAD/transcription start strategies and one `SpeechTimeoutUserTurnStopStrategy` for normal turn completion. Its silence policy is 1.1 seconds, with a 30-second processor watchdog for failure recovery. There is no application end-of-turn timer. On barge-in, Pipecat broadcasts an interruption immediately to cancel speech output; `InterviewSession` cancels in-flight LLM work and invalidates the pending utterance ID. If the interrupted main question had no server output start, the candidate's text is attributed conservatively to the previous question and that unheard main question is retried with a fresh ID. If a partly output prompt is interrupted, the new substantive answer is processed against it. Empty speech and repeat requests retry the interrupted prompt. Explicit skip moves on without fabricating an answer. Spoken end cancels audio and inference, prevents more questions, and uses a separate early closing state. The browser End button closes the peer and microphone immediately, including during connection setup.

## Follow-up turn diagnosis

The inspected real session log shows a follow-up interrupted at event 16, `candidate_final` with only “So the idea” at event 18, `proposal_rejected` at event 20, and question two prepared at event 21. The previous `REHEARSE_TURN_PAUSE_SECS` default was 0.8 seconds. The log lacked VAD and raw STT events, so the exact silence duration and rejected action are unknown. In the installed Pipecat 1.14.0 source, Deepgram final chunks produce `TranscriptionFrame`; `SpeechTimeoutUserTurnStopStrategy` controls turn completion after VAD stop and its configured wait. The controller did not advance merely when the allowance was spent, but the session orchestration converted any rejected proposal into `ADVANCE`. That fallback and the early boundary together caused the visible jump. There is no evidence of duplicate callbacks or a stale LLM reply in the recorded event sequence. The follow-up had no `agent_output_started` event before interruption, despite the user's report that it was heard; check delivery observation in the next live run.

The adapter now retains final segments that arrive before `UserStartedSpeakingFrame`, joins all final segments until one `UserStoppedSpeakingFrame`, and ignores a duplicate stop frame. An incomplete answer can cause a silent `wait`; new speech appends to the same answer. The UI merges continuation turns, while JSONL retains each raw timestamped segment and the inferred boundary. One decision inference is started per completed candidate turn; a resumed candidate turn cancels the previous inference. These are offline-tested changes, not proof that the new 1.1-second setting handles the actual microphone pause.

The new event stream uses one server monotonic clock in milliseconds from session start. Structured `run_inference()` does not expose a first-token event here; browser playback onset is not reliably observable per utterance. These are null rather than guessed. The new logic is covered by mocked regressions only; a real microphone retest is still required.
